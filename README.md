# TRIX Pharmacy — Backend + Barcode + Multi-branch StarterThis is a development starter package, not a deployed production system. It includes:- Express/Node API and PostgreSQL schema- Organization/branch model and branch-scoped access assignments- Email-verification-before-login flow, password hashing, reset tokens and short-lived JWT access tokens- Branch-aware stock batches, FEFO-friendly expiry reports, transactional sales and stock transfers- Barcode/GTIN/SKU product lookup API- Updated TRIX HTML prototype with camera barcode scanning (where browser support permits), keyboard scanner entry and branch/transfer demo screens- Database-backed stock-safety panel for batch quarantine, returns/disposal, routine inspections and saved inspection history- Central medicine reference catalogue and organization product search API## What is and is not connectedThe updated `public/index.html` now has a separate database-connected stock-safety panel. When signed in, staff can select an assigned branch, view PostgreSQL stock batches, quarantine a batch, record a return/disposal, save routine inspections and review saved inspections. The medicine page also has a central database catalogue search. These workflows use authenticated API routes and durable database/audit records. The original dashboard, ordinary stock/sales/purchases, patient/claims and some reports still contain demo/localStorage data. Do not enter real patient data or rely on the demo transaction screens for live operations.The API expects verified products and batch records. A barcode usually identifies a product package; it does not reliably identify the actual lot/batch and expiry. Staff must confirm batch/expiry on the physical package. The camera feature uses the browser `BarcodeDetector` API where available; camera permission normally requires HTTPS or localhost. USB/Bluetooth scanners that behave like a keyboard can be used in the barcode input.## Requirements- Node.js 20+- Docker with Docker Compose (or PostgreSQL 16+)- SMTP credentials for real verification and password-reset emails## Local setup1. Copy `.env.example` to `.env`.2. In `.env`, set a strong `JWT_SECRET` (at least 32 characters), `DATABASE_URL`, `APP_ORIGIN`, `PUBLIC_APP_URL`, and working SMTP settings.3. Set `POSTGRES_PASSWORD` in your shell or add it to a Compose-specific `.env` value. For a simple local setup, use the same password in `DATABASE_URL` and `POSTGRES_PASSWORD`.4. Start PostgreSQL: `docker compose up -d db`5. Install dependencies: `npm install`6. Start the app: `npm run dev`7. Open `http://localhost:3000`.Database initialization runs `db/schema.sql` on first volume creation. If you already created a database without the schema, apply it explicitly with `psql "$DATABASE_URL" -f db/schema.sql`. Do not delete a production database volume to re-run migrations.## Main API routesAll API routes use `/api`. Authenticated routes require `Authorization: Bearer <accessToken>`.### Authentication- `POST /api/auth/register` — creates an organization, main branch and owner account; sends verification link; no access until verified.- `GET /api/auth/verify?token=...` — consumes a short-lived, single-use verification token.- `POST /api/auth/login` — only verified active accounts receive a 30-minute access token.- `POST /api/auth/forgot-password` — generic response to avoid revealing whether an account exists.- `POST /api/auth/reset-password` — uses the expiring token from the email link.- `GET /api/me` — current account.Registration requires SMTP configuration and is deliberately unavailable when email cannot be sent. For a real release, add email-change verification, session revocation/refresh-token strategy, login lockout, stronger abuse monitoring and a support workflow.### Branches and stock- `GET /api/branches` — only branches assigned to the signed-in user.- `POST /api/branches` — owner/admin creates a branch.- `POST /api/branches/:branchId/access` — owner/admin grants an existing same-organization user access.- `GET /api/stock?branchId=<uuid>` — batches for an authorized branch.- `POST /api/products` — add product/barcode mapping.- `GET /api/products/lookup?barcode=<value>` — find product and batch balances by barcode or SKU.- `GET /api/reports/expiry` — organization expiry/quarantine report- `POST /api/stock/:batchId/quarantine` — quarantine a batch with a documented reason and audit record- `POST /api/stock/:batchId/dispositions` — record supplier return or disposal for quarantined/damaged/recalled stock- `POST /api/inspections` and `GET /api/inspections?branchId=` — save and retrieve routine inspection records- `GET /api/catalog?search=` — search curated medicine references and organization products.- `POST /api/sales` — transactional sale; checks branch access, available quantity, batch status and expiry, then records stock movements.- `POST /api/transfers` — moves source quantity to an in-transit transfer record.- `POST /api/transfers/:id/receive` — authorized destination user receives the transfer and destination batch balance is updated.### Sample requestsCreate an organization and owner (SMTP must be configured):```jsonPOST /api/auth/register{  "organizationName": "Example Pharmacy Group",  "branchName": "Musanze Main",  "fullName": "Pharmacy Owner",  "email": "owner@example.com",  "phone": "+250...",  "password": "use-a-unique-password-at-least-12-chars"}```Add a product after signing in:```jsonPOST /api/products{  "name": "Paracetamol",  "strength": "500 mg",  "dosageForm": "tablet",  "barcode": "616110000001",  "sku": "PCM-500-TAB"}```The stock/purchase receiving API is not yet complete in this starter: batches need to be added through a validated receiving workflow before stock can be sold or transferred. Do not insert unverified or fictitious product data into live operations.## Important production hardening still requiredBefore real pharmacy deployment:1. The project is not yet ready for real pharmacy operations.## Subscription plans, payments and owner revenue dashboard### Plans and limitsThe `plans` table is the source of truth for plan prices, feature flags and limits. The seed values in `db/schema.sql` are editable starting prices, not a promise about market pricing:| Plan | Price | Starting limits ||---|---:|---|| 30-day trial | Free for 30 days | 3 branches, 10 users, 1,000 sales/month || Free | RWF 0 | 1 branch, 3 users, 300 sales/month; no stock transfers, advanced reports or data export || Premium | RWF 15,000/month or RWF 150,000/year | 1 branch, 10 users, 5,000 sales/month; advanced reports and data export || Business | RWF 35,000/month or RWF 350,000/year | Up to 20 branches, 100 users, no configured monthly sales cap; stock transfers and advanced reports |Review and update these values in the `plans` seed before launch. Prices are stored in RWF and the current app only has server-side operational enforcement for branch limits, monthly sale counts, and stock-transfer access. The existing prototype still has demo/localStorage workflows for several screens; do not use those demo screens for real pharmacy transactions. The API-backed sales, inventory and stock-control routes are separate from those demo workflows.New registrations receive a 30-day trial. After trial or paid-subscription expiry, protected operational API calls return `402 SUBSCRIPTION_EXPIRED`. The owner can still sign in, inspect billing, choose the limited Free plan, or pay to renew. Free-plan selection sets a long-lived active subscription with server-side limits; it does not delete records. Successful payments extend an existing paid subscription from its current expiry date when that date is still in the future, otherwise from the time of payment verification.### Payment modesThe server supports two modes:- `PAYMENT_PROVIDER_MODE=test`: development-only checkout. It displays a clear test-only page and can simulate a successful payment in the backend. It is deliberately disabled when `NODE_ENV=production` and does not charge real money.- `PAYMENT_PROVIDER_MODE=flutterwave`: server creates a Flutterwave Standard checkout using the secret key, and then verifies the transaction server-side before activating the subscription. The browser redirect is not trusted by itself. The webhook endpoint also checks Flutterwave's `verif-hash` against `FLW_WEBHOOK_SECRET_HASH`, then re-verifies the transaction with Flutterwave. Manual MoMo is separate: customers submit the official MoMo transaction ID, and the platform owner must check the actual incoming transaction in the receiving account before using the Confirm received action. Never approve based only on a screenshot or a customer-entered ID.- `PAYMENT_PROVIDER_MODE=disabled` (or any unrecognized value): Flutterwave/test checkout is unavailable; plan browsing, Free-plan selection, and the manual MoMo request flow remain available.- `MOMO_PAYMENT_NUMBER=+25079829779`: recipient displayed for the manual Rwanda Mobile Money option. This is a user-provided number; verify the account ownership, registered name, and supported payment method before launch. The app does not automatically verify MoMo transactions. A platform owner must check the official receiving-account statement and manually approve each submitted transaction reference before the subscription activates.Flutterwave integration follows its documented hosted-checkout and transaction-verification sequence. See [Flutterwave Standard](https://developer.flutterwave.com/docs/flutterwave-standard-1) and [Transaction Verification](https://developer.flutterwave.com/docs/transaction-verification). Confirm RWF and the payment methods you need are enabled for your own merchant account before accepting payments.### Local setup1.
